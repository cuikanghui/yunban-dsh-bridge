# 在同一台机器上跑多个云班客户端

> 场景：你已经有一个类似的工具（例如把云班消息转到 QQ 的程序），现在又想用本桥接器。
> 两者都用云班账号，**最容易踩的坑不是"同时运行"，而是"同一个账号被两边各自登录"**。

## 一、先判断：是并发问题，还是账号问题

云班的 `x-auth-token` 与 `userUid` 是绑定的。两种典型症状要分清：

| 症状 | 真正原因 | 判定方法 |
|---|---|---|
| `40105 请求未授权` | **token 与 userUid 不匹配**（配置里的账号和登录态里的账号不是同一个） | 看两个客户端各自 cookie 里的账号是否一致 |
| `9999 鉴权失败` | 登录态过期，或被同账号的另一端顶掉 | 重新登录后立刻又失效，多半是被顶 |
| 两边都能跑，互不影响 | 用了**不同账号** | 各自 `listDialogs` 都能成功 |

**关键结论**：同一账号可以在多处登录，但两边"各自登录"时 token 会轮换，先登的那边会掉。
所以要么**共享一份登录态**，要么**各用各的账号**——不要既"各自登录"又"同一个账号"。

## 二、方案 A（推荐）：两个客户端用两个账号

| 实例 | 账号 | 登录态文件 | 浏览器配置 |
|---|---|---|---|
| 桥接器 | 账号 ① | `<桥接器目录>/data/session_cookies.json` | `<桥接器目录>/data/browser-profile` |
| 另一个客户端 | 账号 ② | 它自己的 data 目录 | 它自己的 profile |

要点：

1. **每个实例一份登录态**，绝不指向同一个文件
2. **每个实例一个独立浏览器配置目录**（同一账号共用 profile 会互相刷 cookie）
3. 配置里的 `userUid` **必须等于本实例登录的那个账号**（留空则由程序自动识别，更省事）
4. 桥接器侧把 `云班.登录态共享` 留空（`[]`），它就不会去写别人的文件

桥接器启动时会在日志里写明判断结果：

```
[信息] 其它云班客户端使用不同账号（xxxxxxxx…），登录态互不影响
```

若两边账号相同，则会警告：

```
[警告] 检测到另一个客户端用的是同一个云班账号：xxxxxxxx…
[警告] 两个程序各自登录会互相顶掉（40105/9999）……
```

## 三、方案 B：共用一份登录态

如果确实只能用同一个账号，就只让**一个**程序负责登录，把登录态同步给另一个。

桥接器支持在配置里声明同步目标：

```jsonc
"云班": {
  "登录态共享": ["D:/另一个客户端/data/session_cookies.json"]
}
```

行为：桥接器每次登录成功后，把 token **合并**写入这些文件（不会覆盖对方特有的字段），
并同时把 `userId` 写成目标的 `userUid` —— 因为多数客户端读的是 `userUid`。

> 注意：对方程序多半在启动时把配置读进内存，**同步后要重启它**才生效。

## 四、验证是否真的隔离

```bat
node tools\selfcheck.js
```

托盘菜单「检查整个回路（自检）」的结论区也会附带一行判断。
手工复核的 5 个点：

| 检查 | 做法 | 期望 |
|---|---|---|
| 账号不同 | 看两边 cookie 里的 uid | 不同 |
| token 不同 | 对比 token 前几位 | 不同 |
| 不写对方文件 | 记下对方 cookie 的修改时间 → 重启桥接器 → 再看 | 时间不变 |
| 各自登录互不影响 | 在一个里重登 → 等 5 分钟 → 再看另一个 | 另一个照常 |
| 仅一边掉线 | 弄坏一边的 cookie | 另一边不受影响 |

## 五、已知坑

| 现象 | 原因 | 处理 |
|---|---|---|
| 改完 JSON 解析失败 | PowerShell 的 `Set-Content -Encoding UTF8` 会写 **BOM** | 用 `[IO.File]::WriteAllText(path, text, UTF8Encoding($false))` |
| 改了配置不生效 | 程序启动时读入内存 | 重启该程序 |
| 旧进程占着单实例锁 | 只关了托盘没关主程序 | 一起结束，或删除 `data/bridge.lock` |
